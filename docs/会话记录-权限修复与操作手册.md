## 一、角色权限问题修复

### 问题现象
- 新建「管理员」角色并配置了角色管理菜单与数据权限后，登录该角色的用户看不到已有其他角色；
- 创建用户时角色下拉也选不到任何已有角色。

### 根因
- 角色列表/角色下拉/角色分配的可视范围由**角色树上下级关系**（`pid`/`level`/`tree`）决定（`getManageableRoleIds`），与「数据权限(data_scope)」**无关**；
- 数据权限 `data_scope` 仅被 `FilterAuth`（`internal/library/hgorm/handler/filter_auth.go`）用来过滤业务数据（如用户列表的 `created_by`/`member_id`），从不参与角色列表过滤。

### 改动：`server/internal/controller/admin/role.go`
1. `getManageableRoleIds`：当当前用户任一角色 `data_scope = consts.RoleDataAll(1)`（全部权限）时，返回**除超管角色和自身角色外**的所有角色 id；否则保持原「角色树下级」逻辑。
2. 新增辅助函数 `currentRolesHaveAllScope(ctx, roleIds)`：判断当前用户是否拥有「全部数据权限」。
3. `getManageableRole`：重构为调用 `getManageableRoleIds` 判断成员资格，保证详情/编辑/删除/绑菜单等接口逻辑统一。
4. `ensureCanCreateRoleUnder`：`pid=0`（创建根角色）分支允许拥有「全部数据权限」的角色放行，否则仅超管可建。

### 数据库变更
- `xy_admin_role`：财务文员（id=9）`data_scope` 由 `0` 改为 `1`（全部权限），使其与管理员（id=6）一样可看到/管理除超管外的全部角色。
- 说明：`data_scope` 0 与 1 在 `FilterAuth` 中行为一致（均不过滤/全可见），故无额外副作用。

### 设计边界（后续留意）
- 「全部权限」角色仍看不到/管不了自身角色（与既有语义一致，防止误删自身角色）。
- 超管（`super_admin`）角色永远不可见/不可管。
- 角色「分配菜单」仍受 `getAssignableMenuIds`（自身菜单权限范围）约束。

### 生效要求
- `role.go` 为代码改动，需重启后端进程（当前由 GoLand 启动，非 `gf run` 热编译）；数据库改动实时生效。
